## SELECTION DISCIPLINE (pre-registered in `per_market_champion.py`'s docstring, before results)

Naively taking each asset's argmax arm out of ~22 non-baseline candidates × 4 assets = ~88 cells
is a multiple-comparisons fishing expedition — exactly the failure mode `strategies.py`'s own
PRUNED block documents over and over (micro_strict, lead30, ufat_band, micro_cal... every lab
winner that didn't reproduce forward). The rule, fixed **before** the tables below were run:

> An asset gets a **TAILORED champion** (something other than `av_stoikov`) only if that arm
> beats `av_stoikov` **head-to-head on that asset** — paired per-day (arm's window net) minus
> (av_stoikov's window net) — with:
> 1. day-clustered **t >= 3.0**
> 2. positive on **>= 70%** of days
> 3. **>= 10 days** of head-to-head data (so a 2-day fluke can't pass; same floor `per_asset_edge.py`
>    already uses for "enough day-observations to trust a t-stat")
>
> Fail any leg → champion **defaults to `av_stoikov`**. No exceptions for "the mean delta looked
> good" — this is deliberately a *harder* bar than the vs-baseline promotion bar in `strategies.py`
> (t>=2, days+>=60%), because dethroning an already-validated month-long champion should cost more
> than clearing the null.

Result: on every asset, **every** evaluable challenger's head-to-head t-stat vs `av_stoikov` is
**negative** — not just "not significant," actively worse. `mo_size`, the #2 global arm and the
only other arm with a full 33-day record, is beaten by `av_stoikov` head-to-head on all four
assets (see table above). No tailored champion clears the bar anywhere.

### New-roster arms: not yet evaluable (correctly, not silently dropped)

14 arms only exist in the post-2026-07-11-evening roster and have **2 days** of data as of this
run (`as_cap100, as_k_2x, as_k_half, as_markout, as_resv, as_spread, late_boost, mo_k_2x,
mo_k_half, mo_skew99, queue_gate, skew99, vol_size, xnet`). They fail selection-discipline leg 3
(`n_days >= 10`) by construction — 2 days cannot support a trustworthy day-clustered t regardless
of how the numbers look (and several DO look eye-catching, e.g. BTC `mo_k_half` day-t=+133 on
n=2 days — a textbook small-n mirage, not evidence). They stay on `strategies.py`'s own
pre-registered forward-promotion track (**>=14 forward days, day-clustered t>=3, gross-positive
>=80% of days, mean edge >= max(av_stoikov, mo_size) same-days**) until they accumulate enough
days to even be looked at here. Revisit after ~2026-07-25 (14 calendar days from the roster
change).

### CRITICAL FINDING: the CURRENTLY DEPLOYED live bot does not run this champion

`.github/workflows/live.yml` (the live BTC workflow, real money) invokes:
```
python -u kalshi_trader.py --asset "$ASSET" --live --size-mode flat --post 1 ... (no --gate, no --skew)
```
Neither `--gate` nor `--skew` is passed, so it silently runs `kalshi_trader.py`'s **defaults**:
`--gate ufat --skew 0.25`. That is **not** `av_stoikov` (`as` / `0.99`), **not** `baseline`
(no gate), and not any arm this analysis or the 32-day verdict validated — it's the CLI's own
un-tuned default gate/skew combination. The shadow-validated champion has apparently never been
the live default. `live.yml.proposed`'s matrix `include:` block has been extended in this pass to
carry `--gate as --skew 0.99` per asset (see below) — copying that file over the real
`.github/workflows/live.yml` is the actual fix, on top of just adding the eth/sol/xrp legs.

### `live.yml.proposed` — matrix extended with the champion flags

```yaml
matrix:
  asset: [btc, eth, sol, xrp]
  include:
    - { asset: btc, gate: as, skew: "0.99" }
    - { asset: eth, gate: as, skew: "0.99" }
    - { asset: sol, gate: as, skew: "0.99" }
    - { asset: xrp, gate: as, skew: "0.99" }
```
and the trade command now passes `--gate "$CHAMPION_GATE" --skew "$CHAMPION_SKEW"` (env sourced
from `matrix.gate`/`matrix.skew`). All four rows carry identical flags today because no asset
earned a tailored champion — the table is per-asset (not one shared constant) specifically so a
future divergent champion is a one-line edit to that asset's row, not a workflow reshape.
